# AGENTS.md

## Назначение

Этот файл содержит проектные указания для проекта invest-toolkit

## Архитектура проекта

- Осовная библиотека `src/invest_toolkit/` содержит отдельные модули, которые разделены по назначению
- весь функционла реализован простыми функциями, которые как правило возвращают pd.Dataframe
- Для логгирования используется логгер `src/invest_toolkit/utils/logger.py` и `src/invest_toolkit/utils/logger_decorator.py`
- использование функций реализовано в ноутбуках `notebooks`

## Источники истины

- `README.md` — единая точка входа по проекту, архитектуре, использованию и правилам разработки.
- `TODO.md` — канонический журнал задач и текущего состояния работы.
- `AGENTS.md` — набор правил для ИИ-агента

Не создавай новые файлы вроде `ARCHITECTURE.md`, `STATE.md`, `PROGRESS.md`, `NOTES.md`, если пользователь явно не попросил об этом.

## Правила работы агента

- Перед изменениями изучай `README.md` и `TODO.md` и `AGENTS.md`
- Любую новую задачу или подзадачу сначала фиксируй в `TODO.md`.
- После завершения работы обновляй статус в `TODO.md`.
- Если по задаче есть важные договорённости для будущих агентов, отражай их в `TODO.md` или в этом файле.
- В `TODO.md` пиши только те задачи, которые связаны с непосредственным редактированием файлов проекта
- Перед изменениями сначала изучать существующую структуру и текущие паттерны в кодовой базе.
- Не делать лишние рефакторинги, переименования и массовые косметические правки без отдельного запроса.
- Предпочитать небольшие, локальные и понятные изменения.
- Если есть несколько путей реализации, выбирать самый простой и поддерживаемый.
- Если нужно принять архитектурное решение с заметными последствиями, сначала коротко описать варианты и риски.
- Не додумывать отдельный функционал, команды или сценарии сверх прямого запроса пользователя. Делать только то, что пользователь явно попросил, и сначала согласовывать любые расширения объёма.
- для устновки библиотек использовать виртуальную среду и `uv`
- Установка проекта через `uv pip install -e .`  в виртуальную среду.
- подробно лошшировть код.

## Ожидания по изменениям

- Сохраняй функциональный стиль кода.
- Не меняй уже существующий код без янвго запроса.
- Если нужно внести изменения всуществующий код, уточни необходимость этого действия

## Стиль кода
- Писать код понятно и явно, без лишней магии.
- Предпочитать короткие функции и модули с одной понятной ответственностью.
- Не вводить абстракции заранее, если они не решают реальную текущую задачу.
- Соблюдать существующий стиль проекта, даже если в изоляции возможен другой вариант.
- Бизнес-логика реализуется функциями, а не классами. Состояние передается явно через аргументы.
- Все функции анализа и трансформации данных должны возвращать pd.DataFrame. Избегать побочных эффектов внутри чистых функций.
- Не вызывать функции io и core напрямую из UI или main.py. Использовать слой оркестрации (orchestration/workflows.py) для сборки бизнес-процессов.
- Каждая функция-workflow должна иметь полный docstring с описанием параметров и возвращаемого результата.
- Каждый модуль io/ и core/ должен содержать блок if __name__ == "__main__": с рабочим примером использования и инициализацией логгера.


### Документирование (docstring):
- Используй многострочные docstrings в формате reStructuredText.
   - Пример оформления:

    def add(a: int, b: int) -> int:
        """Складывает два целых числа.
        :param a: Первое слагаемое
        :param b: Второе слагаемое
        :returns: Сумма a и b.
        """
        return a + b

- Примеры использования (опционально):
- Если уместно, добавляй раздел Example: в docstring.
- Не добавляй лишнего кода (например, тесты или вызовы функций), если это не запрошено.
- Пиши подробные docstrings на русском языке
- в названии функций используй префикс `_` для функций, которые не попадают в публичный api и предназначены для внутренного использовния на уровне модуля.

## Логирование и отладка
- **Обязательное логирование**: Весь значимый код должен быть покрыт логами. Использовать только проектный логгер `utils.logger.Logger` (импортировать как `log`).
- **Декоратор DataFrame**: Для всех функций, возвращающих `pd.DataFrame`, обязательно применять декоратор `@log_dataframe` из `utils.logger_decorator`. Это обеспечивает автоматическую фиксацию структуры и содержимого датафреймов в лог.
- **Уровни логов**:
  - `log.info`: Ключевые этапы выполнения, старт/финиш операций, итоговые метрики.
  - `log.debug`: Детали преобразований, промежуточные состояния, параметры вызовов.
  - `log.warning`: Некритичные аномалии, отсутствующие данные, фолбэки.
  - `log.error`: Ошибки, не прерывающие выполнение потока, но требующие внимания.
- **Формат сообщений**: Сообщения должны быть информативными, на русском языке, содержать контекст (имя функции, тикер, путь к файлу).

## GUI (PyQt6)
- **Базовый стек**: Для интерфейса использовать исключительно `PyQt6` + `qt-material` (тема `dark_teal.xml`).
- **Архитектура UI**:
  - **Обязательная вкладка логов**: Последняя вкладка всегда должна быть панелью логов (`LogPanel`), визуально отделенная от остальных.
  - **Шрифт логов**: В панели логов использовать только моноширинный шрифт (Consolas, SF Mono, Menlo или системный FixedFont). Размер 9pt. Цветовая схема должна соответствовать темной теме.
- **Асинхронность**: Все тяжелые операции (парсинг, расчеты, запросы к API) выполнять строго через наследников `BaseWorker` (`QThread`). Блокировка основного потока запрещена.
- **Кэширование**: Для тяжелых данных использовать паттерн кэширования из `ui/cache.py` с подменой функций на уровне импорта.
- **Виджеты**: Переиспользовать стандартные компоненты из `ui/widgets.py` (`FileSelector`, `CheckableComboBox`) для единообразия UX.
